## 1. Цель и сценарий

ExtraHorizon — адаптивный AI tutor. Он использует камеру, чтобы **локально оценивать эмоции пользователя и интегрировать их в основной промпт и всё это в риалтайме**, и меняет стиль объяснения LLM, когда сигнал устойчив. Это экспериментальная оценка поведенческих признаков, а не достоверное определение внутреннего состояния человека. 
Используй Python для Core системы кода, но не забывай про оптимизацию. Для UI Svelte и Go и стиль из F:\TinyTools2\AzIAIBetter, если надо. Всё должно работать в риалтайме и очень быстро

Главный сценарий длится **60–90 секунд**:

1. Пользователь открывает приложение, разрешает камеру и видит работу локального vision-модуля.
2. Пишет: **“Explain recursion to me.”** Получает потоковый ответ AI.
3. После ответа камера фиксирует устойчивый рост *confusion signal* примерно на две секунды. UI показывает изменение оценки и событие **“Possible confusion detected”**.
4. Система предлагает **“Explain differently”**. После нажатия она передает LLM короткий абстрактный контекст и получает другое объяснение: простая аналогия, конкретный пример, короткие шаги. Кнопка надежнее самопроизвольного ответа; автозапуск добавляй лишь после стабильной базовой цепочки.
5. Панель **“Why it adapted”** показывает реальный сигнал, правило срабатывания и примененную стратегию. Timeline показывает фактически измеренные значения и события. Снижение confusion отображай только тогда, когда оно действительно наблюдалось.
6. **Reset demo** очищает чат, состояние, cooldown и timeline перед следующим показом.

Ключевой результат: **camera → local signal → stable event → context → visibly different LLM answer**. Любая второстепенная функция уступает этой цепочке.

## 3. Рамки реализации

**P0:** доступ к webcam, face presence, один честно определенный confusion proxy, сглаживание, срабатывание события, текстовый чат, один LLM, потоковый вывод, adaptive context, наглядная причинная связь, отказоустойчивый чат, reset.

**P1 при наличии времени:** timeline, приятный одноэкранный дизайн, выбор предмета для Tutor Mode, privacy card, короткий pitch.

**Не включай в critical path:** Go-сервис, аккаунты, billing, cloud sync, вторую LLM-интеграцию, voice, обучение собственной модели с нуля, многостраничную аналитику, историю между сессиями, мобильное приложение.

Предпочтительная простая архитектура для нового проекта: **Svelte/SvelteKit → Python/FastAPI → один LLM API**. Камера может передавать уменьшенные кадры с низкой частотой в **локальный backend через localhost**, если vision работает там. Не отправляй кадры, фотографии лица или landmarks во внешний LLM API. Не называй обработку “полностью в браузере”, если фактически она происходит в Python-процессе на том же компьютере. API-ключ остается только на сервере в переменной окружения. Если запускается удаленный backend, утверждение “video never leaves device” неверно: в таком режиме не показывай его в UI.

Сначала исследуй совместимость библиотек и доступный код. MediaPipe подходит для face landmarks/presence, но **сам по себе не классифицирует “confusion”**. Выбери доступную локальную модель либо явно опиши эвристику как *proxy*; не представляй произвольное соответствие эмоций или движений головы как доказанный классификатор. Если надежный proxy за отведенное время не получается, оставь корректное состояние “uncertain”, сохрани рабочий чат и отдельно обозначь ручной **Demo simulation mode** для показа интерфейса. Этот режим должен быть заметно помечен и никогда не выдаваться за живое распознавание.

## 4. Минимальный контракт и логика

Определи и документируй схемы сообщений до работы над UI и backend. Достаточный набор:

```text
GET  /health        → готовность backend и доступность LLM-конфигурации
POST /chat          → поток ответа + метаданные о примененной стратегии
WS   /vision        → локальная передача кадров/сигналов и события состояния
POST /session/reset → сброс состояния текущей сессии
```

Можно выбрать другие маршруты, если существующая архитектура требует этого. Не смешивай состояния разных вкладок или пользователей: у каждой сессии свой буфер, таймер и cooldown. Состояние при отсутствии лица/плохом качестве сигнала — **unknown**, а не “neutral” и тем более не “confused”. Несколько лиц — неоднозначный сигнал: не адаптируй ответ по случайно выбранному лицу.

Для устойчивого события используй сглаживание (например, EMA) и временной порог. Начальные параметры можно взять как рабочие гипотезы: `alpha ≈ 0.2`, `confusion_proxy > 0.65` непрерывно около 2 секунд, cooldown около 15 секунд. Проверяй длительность по времени, а не только по числу кадров. Укажи параметры в конфигурации и подстрой после испытания с реальной камерой. При низкой уверенности или исчезновении лица сбрасывай накопление порога; одно событие не должно повторяться каждый кадр.

При адаптации передавай LLM **только необходимый абстрактный контекст**: наблюдается возможное непонимание, предыдущий способ объяснения мог не помочь, требуется новая короткая аналогия и один пример. Не передавай ложную точность вроде “user is 76% confused” как установленный факт. Разделяй исходный сигнал, решение движка и текст инструкции. Модель не должна утверждать, что точно знает чувства пользователя, или ссылаться на камеру без запроса пользователя.

Предложение “Explain differently” становится активным после события. Повторное объяснение использует историю текущего разговора, избегает дословного повтора и появляется в том же чате. В UI у адаптированного ответа покажи, **какой сигнал был использован и какую стратегию применили**. Если LLM недоступен, выдавай ошибку с действием “Retry”; чат и UI не зависают в бесконечном “thinking”.

## 7. Проверка и тесты

Напиши **небольшой набор содержательных автоматических тестов** для логики, где ошибка сорвет демо:

1. State engine: краткий пик не запускает событие; длительное превышение запускает одно событие; cooldown подавляет повторы; снижение/unknown корректно сбрасывает таймер; две сессии изолированы.
2. Context builder: до события нет adaptive-инструкции; после события есть новая стратегия; кадры/изображения/сырые landmarks не попадают в LLM payload; история предыдущего ответа доступна для переобъяснения.
3. Backend integration с подмененным LLM: поток доставляется до конца, ошибка и timeout завершают loading и позволяют повторить запрос; vision failure не отключает чат; reset очищает все временное состояние.
4. Один короткий frontend/e2e smoke test, если инфраструктура позволяет: вопрос → ответ → событие из управляемого тестового сигнала → адаптация → reset. Управляемый сигнал допустим **только в тесте или явно отмеченном Demo simulation mode**.

Кроме тестов выполни ручную матрицу на реальном устройстве: разрешенная и запрещенная камера; нет лица; несколько лиц; камера отключена во время сессии; websocket оборвался; backend перезапущен; отсутствует API-ключ; LLM timeout; refresh страницы; повторный reset; десять последовательных прогонов основного сценария. Зафиксируй результаты как `pass / fail / not tested` и исправь воспроизводимые проблемы. Если у coding-агента нет доступа к webcam или ключу API, не заявляй, что live demo проверено: запусти автоматические тесты и явно перечисли оставшиеся ручные проверки.

Не добавляй тесты, которые только повторяют строки реализации; проверяй наблюдаемое поведение и отказные пути. После каждого существенного этапа запускай подходящие build/lint/test команды, но не трать последние часы на косметические проверки вместо устранения риска демо.
